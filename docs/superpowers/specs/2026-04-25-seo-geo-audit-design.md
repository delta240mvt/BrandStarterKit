# SEO/GEO Audit and Discovery Layer Redesign

Date: 2026-04-25
Project: Focus Equals Freedom
Scope: Repository-only SEO and GEO audit, redesign spec, implementation planning input
Status: Approved design captured from user review in-session

## 1. Objective

Redesign the repository's discovery layer to maximize SEO and GEO compliance from code alone. This work covers:

- Technical SEO signals generated by the Astro application
- GEO signals for AI crawlers and answer engines
- Content extractability and entity clarity
- Metadata and structured data consistency
- Discovery assets such as `robots.txt`, sitemap, RSS, and LLM-oriented files
- Test and validation guardrails that make compliance enforceable in-repo

This spec does not claim live search performance, live indexation, crawl frequency, Search Console health, Core Web Vitals from field data, or ranking outcomes. Those require deployed environment verification and external tooling.

## 2. Working Definition of "100% Compliance"

For this project, "100% compliance" means the highest practical alignment achievable from repository code and content against current best practices for:

- Crawlability and indexability
- Canonicalization and URL consistency
- Metadata completeness and social sharing readiness
- Structured data correctness and entity coherence
- Internal linking and content discoverability
- AI crawler discoverability and machine-readable summaries
- Deterministic, testable output for all supported page types

It does not mean guaranteed search ranking, guaranteed appearance in LLM answers, or guaranteed parser behavior from third-party bots.

## 3. Current Repository Context

The site is a standalone Astro application deployed to Cloudflare Pages. The repository already includes several discovery primitives:

- `public/robots.txt`
- `src/pages/sitemap.xml.ts`
- `src/pages/rss.xml.ts`
- `src/pages/llms.txt.ts`
- `src/pages/llms-full.txt.ts`
- global metadata and JSON-LD in `src/components/layouts/Base.astro`
- site identity in `src/lib/site.ts`
- regression coverage in `src/lib/standalone-seo.test.ts`

The current baseline is solid, but it is still mostly hand-assembled. Metadata, schema, discovery assets, and content semantics are not yet modeled as strict page-type contracts. The redesign should replace ad hoc assembly with a central SEO/GEO system.

## 4. Recommended Approach

Three approaches were considered:

1. Strict audit plus minimal fixes
2. Audit plus governance layer
3. Audit plus full discovery layer redesign

Recommended and approved approach: option 3.

Rationale:

- The user wants spec, plan, and implementation, not just findings
- The repo is small enough to redesign without excessive migration cost
- Maximum compliance requires structural consistency, not only tactical fixes
- GEO readiness benefits from stronger entity and content modeling, not just `llms.txt`

## 5. Target Architecture

The redesigned system will have five layers.

### 5.1 Site Identity Layer

Central source of truth for:

- canonical base URL and domain
- brand and author identity
- supported languages and locale defaults
- social profiles
- organizational or personal entity type
- reusable descriptions and topical authority statements

`src/lib/site.ts` may remain part of this layer, but it will likely need expansion or decomposition.

### 5.2 SEO Composition Layer

Responsible for deterministic generation of:

- page title
- meta description
- canonical URL
- robots directives
- Open Graph metadata
- Twitter/X metadata
- alternate URLs where relevant
- image metadata and fallbacks
- publication and modification dates

Each page type will consume this layer through a typed contract instead of manually passing loosely related props.

### 5.3 Structured Data Layer

Responsible for page-specific and site-wide schema graphs. This layer will:

- keep entity identity stable across all pages
- define graph composition rules per page type
- avoid schema duplication and drift
- support stronger relationships among site, person, articles, and projects
- improve machine interpretation of the site's topical authority

Likely schema coverage:

- `Person`
- `WebSite`
- `WebPage`
- `Blog`
- `BlogPosting`
- `BreadcrumbList`
- `CollectionPage`
- `AboutPage`
- `ContactPage`
- `SoftwareApplication` where justified by page content

### 5.4 Discovery Layer

Responsible for machine-readable discovery assets:

- `robots.txt`
- `sitemap.xml`
- RSS feed
- `llms.txt`
- `llms-full.txt`
- any additional AI-readable summaries or references justified by repository content

This layer must align exactly with canonical URLs, published content, and page eligibility. No discovery artifact should advertise content that the site does not support cleanly.

### 5.5 Compliance Layer

Responsible for tests and enforcement:

- canonical normalization tests
- sitemap and robots assertions
- page metadata contract tests
- structured data validation-oriented assertions
- content completeness checks for blog posts
- discovery asset consistency checks

The main outcome is that future regressions fail in development or CI instead of silently shipping.

## 6. Page-Type Contracts

The redesign will define explicit SEO/GEO contracts for each page type.

### 6.1 Home Page

Must define:

- clear primary intent
- stable canonical
- home-specific `WebPage` graph
- strong relation to site entity and author entity
- summary of topical authority
- clear internal paths to project and editorial content

### 6.2 Blog Index and Pagination

Must define:

- canonical rules for index and paginated pages
- collection-oriented metadata
- collection schema where appropriate
- crawlable paths to all published posts
- no ambiguous duplication between `/blog` and paginated archives

### 6.3 Blog Article

Must define:

- article-specific title and description
- accurate publication and update dates
- article schema with author and publisher linkage
- canonical URL based on normalized slug
- share image fallback strategy
- internal linking to related discovery surfaces where useful

### 6.4 Legal Pages

Must define:

- clear canonical handling for multilingual or duplicated legal content
- correct noindex/index policy if duplicates are present
- plain extraction-friendly structure

### 6.5 Machine-Readable Endpoints

Must define:

- valid content types
- deterministic generation
- exact consistency with entity and content source-of-truth
- no contradictions between `robots.txt`, sitemap, RSS, and `llms.txt`

## 7. Audit Dimensions

The audit phase will inspect the current repository against the following dimensions.

### 7.1 Crawlability and Indexation Signals

- robots directives
- canonical formatting
- sitemap completeness
- route discoverability
- duplicate URL risks
- indexability of legal and archive pages

### 7.2 On-Page Metadata

- title uniqueness and quality
- description coverage and quality
- Open Graph completeness
- Twitter/X completeness
- `og:image` defaults and suitability
- locale, author, and theme metadata where relevant

### 7.3 Structured Data

- graph completeness
- schema type correctness
- identity consistency
- relation quality across site, author, content, and products
- overreach or unjustified schema usage

### 7.4 Content Extractability

- semantic headings
- content hierarchy
- section labeling
- project and article summary quality
- machine-readable topical signals
- ability for crawlers and LLMs to infer entity-topic relationships

### 7.5 GEO-Specific Signals

- clarity of `llms.txt`
- consistency between `llms.txt`, full summaries, and visible content
- extractable summaries for site and content items
- explicit authorship and expertise signals
- AI-crawler permission clarity

### 7.6 Internal Linking and Information Architecture

- homepage-to-deep-page pathways
- blog and project discoverability
- orphan risk
- navigation clarity
- crawl depth

## 8. Expected Findings to Validate During Audit

Based on the initial repository inspection, the implementation should verify and likely address the following categories:

- metadata logic is too layout-centric and not strongly typed by page type
- current structured data may mix author identity and product entities without a unified content model
- homepage schema may include product nodes whose support in visible content needs verification
- discovery assets likely need stronger cross-consistency checks
- `robots.txt` is permissive and AI-forward, but should be reviewed for standards alignment and unnecessary declarations
- multilingual legal pages may require stricter duplicate or alternate handling
- content authority signals can be made more explicit in page copy and page graph design

These are starting hypotheses, not final findings.

## 9. Error Handling and Failure Policy

The redesigned system should fail loudly when critical compliance data is missing.

Examples:

- missing title or description for a page type
- invalid canonical construction
- post missing publication date
- missing required OG image fallback
- sitemap advertising a route that should not be exposed
- schema graph missing stable entity references

Where hard failure would be too rigid, tests should still emit actionable failures during verification.

## 10. Testing Strategy

Testing will be expanded into four classes.

### 10.1 URL and Canonical Contracts

- homepage canonical
- slash normalization
- blog and legal page canonical rules
- route-to-canonical consistency

### 10.2 Discovery Asset Contracts

- `robots.txt` points to expected assets
- sitemap includes intended URLs only
- RSS references canonical content
- `llms.txt` and `llms-full.txt` resolve with expected headers and content shape

### 10.3 Metadata and Schema Contracts

- each page type renders required metadata
- article pages emit article-specific properties
- schema graph contains expected node types and relationships
- no critical contradictions between metadata and schema

### 10.4 Content Quality Contracts

- required frontmatter completeness
- acceptable article summary availability
- stable slug and date expectations
- no unpublished content leakage into discovery assets

## 11. Implementation Plan Shape

After user review of this spec, implementation planning should cover at least these phases:

1. Baseline audit and findings capture
2. Introduce central SEO/GEO contracts and helper modules
3. Refactor layouts and pages to consume the new contracts
4. Redesign structured data graph generation
5. Redesign discovery assets for consistency and extractability
6. Strengthen content modeling and internal linking where needed
7. Add or expand automated tests
8. Run verification and close remaining gaps

## 12. Deliverables

This spec leads to three concrete deliverables:

1. A repository-only SEO/GEO audit with findings and severity
2. A detailed implementation plan for the approved redesign
3. A code implementation that moves the repository to maximum practical SEO/GEO compliance from code alone

## 13. Constraints and Non-Goals

Constraints:

- no live environment assumptions
- no Search Console or analytics dependence for correctness claims
- preserve repository fit and avoid unnecessary overengineering
- prioritize deterministic output and maintainability

Non-goals:

- guarantee rankings
- guarantee LLM mention frequency
- optimize paid distribution or social campaign mechanics
- broad content strategy unrelated to this site's actual content model
